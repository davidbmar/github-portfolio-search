Weather Integration and Global Preferences

This tutorial details the implementation of a stateful, identity-agnostic weather integration within the 'riff' voice application. It addresses the challenge of persisting user preferences (specifically home city) across sessions without relying on authenticated caller IDs, utilizing a local JSON-backed preference store and a self-contained Open-Meteo API flow.

What was built & why

The development team identified a gap in the 'riff' recording application: the weather feature was marked as 'in-flight' because it lacked both a data source and a mechanism to remember user context. Without a persistent user identity (such as a logged-in account or phone number), the system could not recall a user's preferred location between calls. To resolve this, we engineered a self-contained weather module that decouples data fetching from business logic. We introduced a lightweight, global JSON-backed preference store to save and retrieve the 'home city' locally. The workflow was defined in a YAML configuration where the city-saving action is strictly gated within the 'ask' state, ensuring that preferences are only updated after explicit user interaction. This approach allows the application to provide personalized weather updates immediately upon subsequent interactions, even for anonymous users.

Principles

  • Statelessness vs. Local Persistence: When global identity is unavailable, use local, file-based storage to maintain session continuity for non-sensitive preferences.
  • Dependency Injection for Testability: Decouple external API calls (fetchers) from tool logic to allow for easy mocking and unit testing without hitting live endpoints.
  • Safety-First State Mutations: Restrict write operations (like saving preferences) to specific conversational states (e.g., 'ask') to prevent accidental data overwrites during passive listening phases.

Patterns

  • JSON-Backed Preference Store: A simple, file-system based key-value store for persisting user settings across process restarts or sessions.
  • Injectable Fetcher Pattern: Abstracting HTTP clients behind interfaces to enable deterministic testing of business logic.
  • Self-Contained Flow Module: Encapsulating all related logic (API tools, preference handling, flow definition) into a single domain module to reduce coupling.

How to apply

  • Implementing a 'favorite song' feature in a music bot where the user's choice is saved to a local JSON file after they explicitly confirm it in a dialogue turn.
  • Building a news briefing skill that remembers a user's selected topics (e.g., 'tech', 'sports') across daily calls without requiring account creation.
  • Creating a configurable timer assistant where default durations are stored locally and updated only when the user explicitly says 'set default to 10 minutes'.

Pitfalls

  • Race Conditions in File I/O: Writing to a shared JSON file from concurrent processes can lead to data corruption; ensure atomic writes or file locking mechanisms are in place.
  • Privacy Leakage: Storing PII (Personally Identifiable Information) in a global, unencrypted JSON store is a security risk; limit persistence to non-sensitive preferences like city names or units.
  • Over-Reliance on Implicit Context: Assuming a saved preference applies to all contexts may lead to errors; always allow users to override saved defaults with explicit commands in the current session.
